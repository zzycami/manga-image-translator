# 漫画翻译“错位”问题分析与修复

> 现象：线上偶尔出现“请求页 A，返回页 B 的译文/译图”；老接口（`full` 整图）
> 出现较多，新接口（`json_stages`）未出现。
> 修复 commit：`98168f5`；部署加固 commit：`3531de1`。

## 1. 现象与结论速览

| 现象 | 根因 | 修复 |
|------|------|------|
| **请求 A 收到 B 的整页结果（串台）** | 翻译子进程共享 `progress_queue`，上一个请求中断后残留结果帧被下一个请求读到 | 每请求独立结果队列（`mode/share.py`） |
| **同一张图内文字画到错误区域** | 翻译器按 LLM 响应“顺序”映射、丢弃 `<|N|>` 编号；报错/重试时 LLM 更易乱序/缺号 | 按编号归位 + 畸形重试/报错（`translators/`） |

线上实际观察到的“A→B”属于**第一条（整页串台）**；第二条是同类场景下会静默产出
“同图错位”的潜在 bug，一并修复。

## 2. 根因一：整页结果串台（共享队列陈旧帧）

### 代码路径

- `manga_translator/mode/share.py`：`MangaShare` 只有一个 `asyncio.Queue`
  （`progress_queue`），所有请求共用。
- 每个 `/execute/{method}` 请求通过 `progress_stream()` 从**同一个**队列读帧，
  读到 status=0（结果）或 2（错误）即结束。

### 触发链路

1. 请求 A 在翻译中途被断开（调用方超时/报错关闭连接），但子进程仍在后台完成翻译；
2. A 的流式响应生成器已取消，A 的结果帧留在共享队列里无人消费；
3. 下一个请求 B 获得同一执行器，`progress_stream()` 先读到 **A 的陈旧结果帧**，
   立即结束——B 收到了 A 的整页结果。

### 为什么新增的 hash（`request_id` / `sourceImageMd5`）拦不住

status=5 的 meta 帧是**按当前请求参数生成的回显**：

- 请求 A 发出时，服务端回显“A 的 request_id + A 的图 md5”；
- 即使最终交付的是 B 的陈旧结果，meta 依然写着 A 的 id/md5，校验必然通过。

meta 只能证明“服务端收到了 A 的请求”，证明不了“交付的结果真的来自 A 的处理”。
而老接口返回的是整张 PNG，结果里没有任何可校验标识，所以 A→B 无法被发现。

### 为什么新接口（`json_stages`）没出现

stages JSON 里的 `sourceImageMd5` **不是回显，而是实际处理那页的上下文属性**
（`ctx.translation_stages` 在子进程内用该页自己的 config md5 生成）。若 A 收到 B 的
陈旧 stages，JSON 里嵌的是 B 的 md5，客户端比对本页 md5 即可发现并重新查询。

## 3. 根因二：译文按响应顺序映射（同图错位）

### 代码路径

翻译流程：OCR 得到 N 个文字区域 → 文本按顺序拼入 prompt（带 `<|1|>、<|2|>…` 编号）
→ LLM 返回译文 → `zip(ctx.text_regions, translated_sentences)` 写回区域。

旧解析器（`custom_openai` / `deepseek` / `chatgpt`）都用
`re.split(r'<\|\d+\|>', response)` 切分：

- **编号被丢弃**，假设“响应顺序 = 请求顺序”；
- LLM 在报错、超时重试、批处理拆分后，容易输出**乱序 / 缺号 / 重复 / 带前言**的
  编号列表，此时按位置映射会把 A 区域译文塞进 B 区域；
- `chatgpt` 的“严格校验”只检查索引**集合**齐全、无重复，**不检查顺序**，乱序照常放行。

这与“为什么偶尔、且翻译接口报错时更容易出现”完全吻合。

## 4. 修复方案

### 4.1 每请求独立结果队列（修串台）

`manga_translator/mode/share.py`：

- 每个请求创建自己的 `asyncio.Queue`；
- 进度 hook 只写当前活跃请求的队列；结果帧写进同一队列；
- 单例锁保证同时只有一个任务执行，因此“当前活跃队列”成员安全；
- 上一个请求中断后的残留帧不可能再被下一个请求读到。

### 4.2 按编号归位（修同图错位）

新增公共解析 `parse_indexed_translations`（`translators/common_gpt.py`）：

- 捕获每行的 `<|N|>` 编号，把译文放回**对应索引**，不信任响应行顺序；
- 编号缺失 / 重复 / 越界 / 空译文 → 判定畸形 → 重试；重试耗尽 → **报错**，
  而不是静默错位；
- 支持编号前前言、单行译文换行续接、CJK 续行不加空格。

接入三个翻译器：

- `custom_openai.py`：畸形响应最多重试 3 次（`_PARSE_RETRY_ATTEMPTS`），仍失败抛错；
- `deepseek.py`：畸形/缺号按原有重试→拆批逻辑继续，按索引写回；
- `chatgpt.py`：校验索引集合后，再按编号映射（含 fallback 模型路径）。

### 4.3 回归测试

`test/test_translation_order.py`（13 条）：

- 乱序响应 → 按编号归位正确；
- 缺号/重复/越界/空译文 → 判定畸形；
- custom_openai / deepseek：畸形后重试成功、持续畸形抛错、单查询无编号兜底。

## 6. 关键经验

1. **“校验”要绑定结果，而不是回显请求**：request_id / sourceImageMd5 的 meta 帧是
   请求参数回显，无法发现结果串台；新接口之所以能自愈，是因为 stages 内嵌的是
   **实际处理页**的 md5。
2. **LLM 响应不能按位置信任**：编号列表必须按编号归位，畸形宁可重试/报错，
   不可静默错位。
3. **共享队列是跨请求状态的坑**：任何“一次一个任务”的执行器，其结果通道也必须
   按请求隔离。
